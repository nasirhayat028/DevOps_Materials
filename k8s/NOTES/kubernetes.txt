The app pod in the elastic-stack namespace currently writes logs to /log/app.log.
Your task is to add a sidecar container that will ship these logs to Elasticsearch.

Requirements:

Add a sidecar container named sidecar to the existing app pod.
Use the image: kodekloud/filebeat-configured.
Mount the log volume: The existing log-volume must be mounted to the sidecar container at /var/log/event-simulator/.
Implementation: Define the sidecar as a Kubernetes native sidecar container using initContainers, and set the restartPolicy to Always.

Important Notes:

You will need to delete and re-create the pod to add the sidecar container.
Do not modify the existing app container or volume configuration.
The sidecar should be defined as an initContainer and must run continuously alongside the main application container
Refer to the diagram below for your configuration.
Reference Documentation:

Sidecar Containers: https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/
Note: State persistence concepts are discussed in detail later in this course. For now, follow the pattern shown in the reference documentation.

_______________
apiVersion: v1
kind: Pod
metadata:
  labels:
    name: app
  name: app
  namespace: elastic-stack
spec:
  initContainers:
  - name: sidecar
    image: kodekloud/filebeat-configured
    restartPolicy: Always
    volumeMounts:
      - name: log-volume
        mountPath: /var/log/event-simulator

  containers:
  - image: kodekloud/event-simulator
    name: app
    resources: {}
    volumeMounts:
    - mountPath: /log
      name: log-volume

  volumes:
  - hostPath:
      path: /var/log/webapp
      type: DirectoryOrCreate
    name: log-volume

1. Multi-Container Pods (Kya hote hain?)
Jab aik hi Pod ke andar aik se zyada containers chal rahe hon, to usay Multi-container Pod kehte hain. Ye containers hamesha aik saath start hote hain, aik saath move hote hain, aur aik hi network (IP address) share karte hain.
Kyun use hote hain? Jab do processes ka aapas mein itna gehra talluq ho ke wo aik dusre ke baghair kaam na kar saken (maslan: aik app aur uska log collector).
2. Init Containers (Kyun, Kaha aur Kaise?)
Kya hote hain?
Init containers wo containers hote hain jo "Main Application Container" ke chalne se pehle apna kaam khatam karte hain. 
Rule: Init container ka apna kaam poora karke exit hona zaroori hai. Agar ye fail ho gaya, to main container kabhi start nahi hoga. [1, 3] 
Kyun use karte hain? (Use Cases)
Setup/Preparation: Main app ke liye koi file download karni ho ya directory banani ho. [1]
Dependency Check: Ye check karna ke Database ready hai ya nahi. Jab tak DB ready nahi hoga, Init container wait karega aur app start nahi hone dega. [1, 2]
Security: Kuch sensitive kaam jo aap main container mein nahi dikhana chahte, wo init container mein karke khatam kar den. [2] 
Kaise use karte hain? (YAML Example)
Iska tarika ye hai ke aap YAML file mein spec ke andar initContainers ka section add karte hain. 
yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
spec:
  # Ye pehle chalega
  initContainers:
  - name: install-tools
    image: busybox
    command: ['sh', '-c', 'echo "Tools Installing..." && sleep 5']

  # Ye tab chalega jab upar wala finish ho jaye
  containers:
  - name: main-app
    image: nginx
Use code with caution.

3. Mashoor Patterns (Helper Containers)
Multi-container pods mein 3 main patterns use hote hain:
Sidecar: Main app ke sath reh kar uski madad karna (maslan: Logs fetch karna). [3, 4]
Adapter: Main app ke output ko kisi khaas format mein badalna taake bahar ka system samajh sake. [3, 4]
Ambassador: Network proxy ke taur par kaam karna (maslan: App ko bataye baghair traffic ko kisi khaas DB tak pohnchana). [3, 4] 
Khulasa (Summary):
Init Containers: Pehle aate hain, kaam khatam karke chale jate hain. [1, 2]
Main Containers: Baad mein aate hain aur jab tak app chal rahi hai, tab tak rehte hain. [1]
